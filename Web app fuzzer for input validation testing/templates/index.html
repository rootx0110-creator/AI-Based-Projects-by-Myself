How it works

Understanding the detection engine behind the fuzzer.

Detection signals

  • Reflection — payload text echoed back unencoded.
  • Error leakage — SQL, stack traces and framework errors.
  • Timing — sleeps like SLEEP(5) delaying responses.
  • Status shifts — 500s, 400s and redirects from payloads.
  • Content disclosure — file contents (/etc/passwd).

Reading the results

  • High — strong evidence (SQL errors, LFI, time-based).
  • Medium — likely issue (reflections, server errors).
  • Low — suspicious behaviour worth manual review.
  • OK — payload rejected, validation looks solid.

Responsible use

  • Only scan systems you own or are authorized to test.
  • Start with 1 worker and a delay on unknown targets.
  • Payloads are benign by design; no destructive commands.
  • See readme.txt and architecture.md for details.
