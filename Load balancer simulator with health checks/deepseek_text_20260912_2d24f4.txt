Build a complete Windows desktop GUI application (.exe) for a "Load Balancer Simulator 
with Health Checks". The application must simulate a reverse proxy load balancer that 
distributes incoming HTTP traffic across multiple backend servers, continuously performs 
health checks, and visually demonstrates routing decisions, failover, and recovery in 
real time. It must be production-ready, well-architected, and include full documentation.

PROJECT REQUIREMENTS
═══════════════════════════════════════════════════════════════

TECH STACK (choose ONE and justify):
  - Python 3.11 + PyQt6/PySide6 + aiohttp + aioprocessing  →  recommended
  - OR Python + FastAPI (control plane) + CustomTkinter (UI)
  - OR Node.js + Electron + Express + ws
  - OR Go + Wails + net/http/httputil.ReverseProxy
  - OR C# .NET 8 + WPF + YARP (Yet Another Reverse Proxy)

CORE FEATURES:
  1. Load Balancer Core (reverse proxy)
     - Frontend listener on configurable port (default 8000)
     - Backend pool: N mock servers spawned by the app (default 3–5)
     - Each backend binds to 127.0.0.1:<auto-port>, exposes /health and /
     - Real HTTP proxying using ReverseProxy semantics
     - Supports HTTP/1.1 with keep-alive; WebSocket passthrough (optional)

  2. Load Balancing Algorithms (switchable at runtime)
     - Round Robin
     - Weighted Round Robin
     - Least Connections
     - Least Response Time
     - IP Hash (sticky sessions)
     - Random
     - Power of Two Choices (P2C)
     - Consistent Hashing (optional ring visualization)

  3. Health Checking Subsystem
     - Active checks: periodic GET /health with timeout
     - Passive checks: track 5xx rate, timeouts, connection errors
     - Configurable: interval, timeout, success/failure thresholds
     - States: HEALTHY · DEGRADED · UNHEALTHY · DRAINING · DISABLED
     - Auto-removal from pool on UNHEALTHY, auto-re-add on recovery
     - Circuit breaker per backend (open / half-open / closed)
     - Manual controls: force healthy/unhealthy, drain, disable

  4. Traffic Simulator
     - Built-in load generator (configurable RPS, concurrency, payload size)
     - Deterministic seed mode for reproducible demos
     - Traffic patterns: constant, ramp-up, spike, sine wave, burst
     - Mix of endpoints: /fast, /slow, /error, /flaky
     - Injects synthetic latency and errors on backends

  5. Real-Time Visualization Dashboard
     - Topology diagram: Client → LB → Backend nodes (animated edges)
     - Node health badges (color-coded: green/yellow/red/gray)
     - Live sparkline per backend: RPS, latency p50/p95/p99, error rate
     - Global graph: requests/sec, active connections, error %
     - Heatmap: latency over time per backend
     - Live request log with routing decision (algorithm-chosen backend)
     - "Why this backend?" tooltip explaining the routing choice

  6. Scenario Recorder & Replay
     - Record all events (health changes, requests, config changes)
     - Replay with timeline scrubber
     - Export scenario JSON for sharing

  7. Chaos Engineering Panel
     - One-click: kill backend, add latency, drop packets, return 500s
     - Random chaos mode (fault injection at intervals)
     - Auto-recovery timer

  8. Configuration & Persistence
     - JSON config in %APPDATA%/LBSimulator/
     - Save/load scenarios (.lbsim files)
     - Export metrics to CSV / JSON / Prometheus text format

  9. GUI Features
     - Tabs: Dashboard · Backends · Algorithm · Health · Traffic · Logs · Settings
     - Dark/light theme toggle
     - System tray with status summary
     - Hotkeys: start/stop simulator, reset, snapshot
     - Multi-window: undock topology view

NON-FUNCTIONAL:
  - Fully async (asyncio) core; GUI never blocks
  - Deterministic timing under load (monotonic clock)
  - No memory leaks — bounded log ring buffer
  - Bundle as a single .exe (no console window)
  - Include app icon (.ico)
  - Build script (build.bat / pyinstaller spec)
  - Cross-platform core, Windows-first packaging

HEALTH CHECK STATE MACHINE
═══════════════════════════════════════════════════════════════

States:
  HEALTHY     — passing active + passive checks
  DEGRADED    — passing active, elevated 5xx or latency (warn threshold)
  UNHEALTHY   — failing active checks or circuit open
  DRAINING    — removed from new routing, finishing in-flight
  DISABLED    — manually disabled, not probed, not routed

Transitions:
  HEALTHY  → DEGRADED   : N consecutive warn responses or passive error rate > X%
  DEGRADED → HEALTHY    : M consecutive OK responses
  DEGRADED → UNHEALTHY  : K consecutive failures
  UNHEALTHY→ HEALTHY    : K consecutive OK responses (half-open probe)
  Any      → DRAINING   : manual drain
  DRAINING → DISABLED   : in-flight = 0
  DISABLED → HEALTHY    : manual enable + first check OK

Circuit Breaker (per backend):
  CLOSED     → OPEN      : error rate > threshold over rolling window
  OPEN       → HALF-OPEN : after cooldown
  HALF-OPEN  → CLOSED    : probe succeeds
  HALF-OPEN  → OPEN      : probe fails

    ) -> Backend: ...
